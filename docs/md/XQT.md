# XQT 模型优化工具链

本文保留为 `XQT` 的兼容长期事实源. 新的 Markdown 主导航已经迁到 [index.md](index.md), 并按架构 / 说明 / 使用三层组织.

XQT 只关注模型本身. 它接收 PyTorch 模型,checkpoint 或导出产物,执行模型侧压缩,图变换,导出适配,误差分析和 benchmark. 训练,QAT,finetune,distillation,recovery,dataset / dataloader,training provider 和 evaluation provider 不属于 XQT.

需要梯度更新的流程归 XDL 或第三方训练工具,再把训练后的模型或 checkpoint 交给 XQT.

在本仓库内, XQT 是唯一推理优化主体. Python API 是主入口: `XQTOptimizationSession`, `xqt.convert(...)`, 当前真实的 `xqt.nn.*` semantic facade 用来表达模型替换, 算子 contract, runtime intent 和 benchmark/report. `triton`, `tilelang`, `cutlass`, `cute_dsl`, `cutile`, `custom_cuda` 是 XQT 内部 engine, 不是和 TensorRT / ONNX Runtime / OpenVINO 并列的外部 backend.

当前 `XQTOptimizationSession` 内部已经维护正式 `SessionStage` 图, `StagePayload` typed payload, transform-side provider 和 `StageComparison` helper. 详细协议以 [architecture/xqt.md](architecture/xqt.md) 和 [../../xqt/FRAMEWORK.md](../../xqt/FRAMEWORK.md) 为准.

后续修改规划见 [XQT 改进路线图](architecture/xqt-improvement-roadmap.md) 和 [改进目标与验收](architecture/xqt-improvement-goals.md). 规划将状态正确性, 契约接线和真实模型交付串成逐项验收路径, 不代表这些目标已实现.

## 3. 当前可用能力

本章节保留为兼容锚点. `XQT` 的能力地图和概念说明已经迁到:

- [explanation/xqt-concepts.md](explanation/xqt-concepts.md)

如果你要更新当前能力范围, 半可用 / 实验性状态或能力地图, 优先更新上面的说明层页面.

当前 `TileLang` 的受限 kernel target 已覆盖 `attention`, `conv`, direct FP16/BF16 `linear`, `linear_marlin`, direct half `LayerNorm`, `dequant_gemm_epilogue` 及 packed FP4 / NVFP4 变体. 这些 pattern 不是同等成熟度: `attention` 已有受限 CUDA FP16/BF16 kernel 入口,要求 Q/K/V dtype 匹配,`dropout_p=0`,`seq_kv >= seq_q`,且 BF16 `head_dim` 必须 16 对齐;direct dense `linear` 接受匹配的 FP16/BF16 activation,weight,bias 和 output,使用 FP32 accumulator,允许 partial M/N,但 K 必须能被 `block_k` 整除. `conv` 当前是 `torch.unfold` / im2col 加 TileLang half GEMM 的 lowering 路径而不是 fully fused conv,direct half `LayerNorm` 已接入 TileLang `reduce_sum` kernel 且限制为 last-dim FP16. CPU 路径只使用 PyTorch eager fallback.

BF16 Attention 已在 RTX 4070 Ti SUPER `sm_89` 上完成 5-shape x 9-candidate sweep 和 9 x 31 paired gate. 默认仍为 `64x64/128 threads/2 stages`;相对 BF16 SDPA,medium/causal/decode 稳定降低 `11.85%/38.87%/42.15%`,small 稳定慢 `8.33%`,long 的 `2.07%` 差距低于 promotion 门槛. 因此显式 TileLang BF16 可执行,但 Ada `attention_fastpath="auto"` 仍选择 native SDPA,不增加仅由 synthetic kernel matrix 驱动的 shape heuristic. 证据见 `research/xqt-gemm/artifacts/2026-08-09-sm89-tilelang-attention-bf16/`.

新增 Triton forward-only attention engine,契约为 contiguous BHSD,匹配 FP16/BF16 Q/K/V,FP32 score/online softmax/output accumulator,`head_dim=16/32/64/128`,`seq_kv >= seq_q`,`dropout_p=0`,非方形 causal 使用 lower-right semantics,不支持 backward. SM89 5-shape x 19-candidate sweep 的 correctness 最大绝对误差为 `0.00390625`;只为 decode 增加两个 exact resolver preset:FP16 `16x64/4 warps/2 stages`,BF16 `16x128/4 warps/2 stages`. 五个独立 seed 的 resolver-vs-default audit 均为 `9:0`;long prefill 的 stages=3 跨 seed 有低于 3% 的 case,因此撤回. 初始 paired gate 中 Triton 相对 SDPA 的 causal/decode latency 分别降低 FP16 `22.63%/62.27%` 和 BF16 `21.01%/67.02%`,但 TileLang 仍快 `48.53%/13.58%` 和 `43.75%/10.00%`;small/medium/long prefill 不进入 Triton 默认路由. 后续 actual exact resolver 的 5-seed engine-entry audit 也只稳定胜过 SDPA:FP16/BF16 对 SDPA gap 为 `35.78-40.40%`/`40.09-45.86%`,而对 TileLang 不满足全 seed promotion 条件. 因此 Triton attention 目前是显式 engine,`attention_fastpath="auto"` 和既有 TileLang/native SDPA 路由保持不变. 证据见 `research/xqt-gemm/artifacts/2026-08-09-sm89-triton-attention/`.

wrapper/runtime 分层 profile 进一步确认 direct attention kernel 不是完整 MHA 的主要 latency 来源:在 `B1,H8,Sq1,Skv1024,D64,causal` 上,FP16/BF16 TileLang full forward 为约 `0.104/0.112 ms`,native lower-right full forward 为约 `0.132/0.133 ms`,而 projection,layout copy 和 wrapper/module 入口占据其余时间. 首次 profile 发现 native 非方形 causal 误用 upper-left SDPA mask,已改为共享 helper 显式调用 `causal_lower_right`;修复后 native,TileLang 和 Triton 全部通过 lower-right correctness. 该 profile 是 sequential 分层证据,不覆盖 5-seed `9 x 31` paired engine gate,所以不改变 `attention_fastpath="auto"`.

ConvRot/SVDQuant 另新增 SM89 专用 native CUDA 动态融合路径,不依赖 Python 算子组合或 `torch.compile`. ConvRot W8A8 在同一前端 kernel 内完成 regular-Hadamard rotation 和 dynamic per-token INT8 quant,再由同一次 C++ dispatch 进入 packed W8A8 GEMM. SVDQuant W4A4 直接采用 Nunchaku 两阶段 FUSE_DOWN/FUSE_UP:第一阶段融合 dynamic W4 activation quant 与 LoRA down,第二阶段融合 W4A4 GEMM,LoRA up 和 bias;W8A8 路径对应融合 dynamic INT8 quant + LoRA down 和 INT8 GEMM + LoRA up/bias. RTX 4070 Ti SUPER `sm_89` 的 3-shape CUDA-event gate 中,ConvRot W8A8 相对同契约 split baseline 为 `1.51x-1.91x`,SVDQuant W4A4 为 `1.44x-1.73x`,SVDQuant W8A8 为 `1.14x-1.19x`;W4A4 的 C++ bound runner 与 direct Nunchaku-fragment floor 的差异为 `-2.52%` 到 `+0.17%`,完整 wrapper 与 strict floor 的差异不超过 `2.22%`. 证据见 `research/xqt-gemm/artifacts/2026-08-10-sm89-convrot-svdq-fusion/`.

2026-08-18 的 quant/runtime 解环后,`Int8MmaLinear` 与 `W4StorageInt8MmaLinear` 的 quant 产物是 `xqt.contracts` reference storage shell;同名 runtime execution view 通过 `from_storage()` 显式 materialize. 上述 ConvRot CUDA 数据仍是已验证 kernel 证据,但 quant artifact 不再直接执行 runtime fastpath;ConvRot 专用 execution view 完成迁移前,通用 quant/workflow 路径只声明 reference forward,不能把历史 kernel gate 写成当前自动路由收益. materialize infer-facing runtime view; RTX 4070 Ti SUPER (`sm_89`) 的
`engine=auto` 实测 294 个 Linear 全部选择 `tilelang`, P50 generate 约 `1951 ms`,
相对 storage shell 的 `3580 ms` 明显降低,但仍慢于 BF16 baseline 的 `1039 ms`,
因此暂不提升为默认 INT8 route.

MiniCPM5-2B 已接入 XQT 模型 profile `hf.minicpm5-2b`,使用标准 Transformers `LlamaForCausalLM` loader. 模型侧实验覆盖 BF16 baseline,AWQ/GPTQ W4A16,FP4 W4A16 和 W8A8 INT8;默认保护 `lm_head`,并支持 MLP-only 与首尾层保护的混合精度策略. RTX 4070 Ti SUPER `sm_89` 实测中,AWQ group64 的全模型候选 logit RMSE 为 `1.28`,MLP-only 为 `1.16`,首尾 2 层及 attention 保护为 `0.96`;对应 P50 generate latency 分别约 `1129/1181/1147 ms`,BF16 baseline 约 `1045 ms`. 这些是单 prompt held-out logit proxy,不是任务准确率. W8A8 INT8 已修复 CUDA `torch._int_mm` 的 17-row prefill 对齐,当前实际执行仍为 `torch_int_mm` reference,全模型 P50 约 `3626 ms`,不能写成 native INT8 加速. 证据见 `artifacts/xqt/inference/minicpm5-2b/`,入口见 `examples/xqt_models/minicpm5_2b_quant_benchmark.py` 和 `minicpm5_2b_mixed_precision.py`.

2026-09-10 的 W4A16 decode 重写后,`materialize_minicpm5_weight_only_runtime(..., engine="cuda")` 是 sm_89 上的默认混合路由: decode 行 (M<=8) 走仓库内置的 FasterTransformer 风格 native W4A16 GEMV (`xqt/kernels/jit/csrc/quantization/awq_w4a16_sm89_kernel.cu`, lop3 寄存器解包, fp16/bf16 双支持, signed 存储 XOR 0x88 + zero-point 8 桥接), M>8 走 dense cache. 微基准 M=1: MLP gate/up `4.06x`,down `3.90x`,qkv/o `1.39x` 相对 dense BF16 GEMV,数值误差等于量化下界. TileLang fused fp4 kernel 已重写为 K 分块流水线 (O(block) shared),在 sm_89 可运行 (约 124 GB/s),通过 `engine="tilelang"` 显式选择,作为 fp16 后备路径;旧实现 O(K) shared 分配在 sm_89 上设计性不可运行的问题已修复并加 fail-fast. e2e generate (64 token) 实测 `1219 ms`,慢于 dense-cache 的 `1061 ms` 与 BF16 `1046 ms`: 2B 模型 M=1 的 GEMM 只占 e2e 约三成,hybrid Python dispatch 与 HF generate 框架开销吞掉 kernel 收益,不能写成端到端加速. 零校准下界实测: RTN w4g64 logit RMSE `1.54`,5-prompt AWQ `1.32`,RTN w8g128 `0.13`;QuaRot 离线旋转对 weight-only RTN 几乎无收益 (`1.52` vs `1.54`). 完整证据与未采纳方案见 R-050 (`docs/md/explanation/operator-optimization-records.md`),复跑入口见 `examples/xqt_models/minicpm5_2b_quarot_benchmark.py` 与 `minicpm5_2b_zerocal_benchmark.py`.

2026-09-10 的 8000 字符英译中任务级评测补齐了 "只有单 prompt logit proxy, 没有任务指标" 的缺口,同时暴露了 W8A8 的真实状态. 同一篇 7976 字符英文文档 (7 节, 自撰多主题) 在八个档位上做单次 greedy 生成; 质量按与 BF16 译文的字符级一致性计算, 没有人工参考译文. 结果: BF16 e2e `26.3 s` (55.5 tok/s), AWQ W4A16 dense/native `27.2 s`/`29.4 s` (char BLEU-4 `0.60`), MLP-only/首尾保护 `30.2 s`/`28.0 s` (`0.66`/`0.70`), 这些档位的译文都完整收敛. 朴素 W8A8 与离线 QuaRot+W8A8 分别 `129.1 s`/`153.2 s` 且译文坍塌为英文元评论 (char BLEU-4 `0.002`/`0.003`); 对照实验显示 tilelang 与 torch_int_mm 在同一权重同一输入上的 logits 完全一致 (RMSE 同为 `3.57`), 坍塌来自 W8A8 的动态 per-tensor 激活量化本身 (历史单 prompt logit RMSE 约 `3.2` 已有记录), 不是 engine 选择问题. ConvRot 在线旋转 + native SM89 small-M 执行视图是本次唯一可用的 INT8 路线: char BLEU-4 `0.874`, ROUGE-L `0.922`, token 一致率 `0.898`, 但 e2e `185.9 s` (7.8 tok/s), 比 BF16 慢约 7 倍; decode 每 token 实测约 `128 ms`, 权重读取 roofline 约 `6 ms`, 仍有一个数量级以上的余量. 结论: sm_89 上 INT8 旋转的精度潜力已验证 (明显好于 W4A16), 当前瓶颈完全在 decode 运行时, 不能写成 INT8 e2e 加速. 方法学要求: 这类 instruct 模型必须经 `apply_chat_template` 渲染, 直接 tokenize 拼接 instruction 会退化成英文续写; 对照评测必须同权重同输入同模板, 否则会把 harness 问题误读成量化结论. 评测入口见 `examples/xqt_models/minicpm5_2b_translation_eval.py`, 产物见 `artifacts/xqt/inference/minicpm5-2b/translation_eval.json` 与同名 `.md`, 运行时判定细节见 R-051.

2026-09-10 的 CUDA graph decode 运行时把量化收益兑现到了端到端, 随后又用投影融合与 W4 LM head 把 e2e 推到 `3.07x`. 新增 `xqt/runtime/graph_decode.py` 的 `CudaGraphDecodeSession`: 自建 static-KV decode step (逐 token 与 HF eager 语义等价), 每个 256 长度桶一张 CUDA graph; 未写满槽位保持 K=0/V=0, 用值掩码 SDPA `R = SDPA(q, K_pad, v_mask)` 做零填充自校正 `out = X / R`, 在纯 torch 环境把变长前缀注意力变成静态形状 (bf16 相对误差约 `2e-3`), 图内含动态位置写缓存与 argmax 原地更新, replay 每步无 Python. 同一 7976 字符文档 (prompt 1715 token, greedy 约 1470 token): BF16 eager `26196 ms` (55.6 tok/s) -> BF16 graph `16240 ms` (steady 88.2 tok/s); AWQ W4A16 native eager `30844 ms` (48.2 tok/s) -> W4A16 graph `7811 ms` (steady `180.4 tok/s`, 预捕获 13 桶约 `250 ms`), 相对 BF16 eager e2e **`3.35x`**, 相对同一运行时的 **bf16 graph** 基线 e2e `2.08x` / steady `2.05x` (两次运行 `2.08-2.13x`) (两条 graph 路线共用同一组融合, 比值只反映量化收益). 三项优化都经 ncu/实测确认瓶颈后落地: `AWQW4A16Linear.from_signed_groupwise_storages` 把 q/k/v 与 gate/up 解码 GEMV 融合 (每 token 294->168 个 kernel, 输出逐位一致), `quantize_minicpm5_lm_head_w4` 把 BF16 head (每 token `0.53 GB`, ncu DRAM `92.4%` 已到 roofline) 换成 W4A16 (`0.13 GB`, kernel `0.89-1.01 ms -> 0.25 ms`), 以及融合 `F.rms_norm` 替代 HF 的 7-kernel 复合 RMSNorm (`5.23-5.32 -> 4.69-4.72 ms/token`, 默认 `fuse_norms=True`, 关掉该开关可回到逐 token HF 等价). 质量保持: 对 BF16 译文 char BLEU-4 `0.600` / ROUGE-L `0.765`, 与 eager 量化路线的 `0.605` / `0.767` 同水平; greedy token 序列与 eager 因 bf16 数值路径差异而漂移, 需要逐 token 复现 HF 时可用精确前缀变体, 但每长度捕获 `13 ms` 使 e2e 反而不达标. 适用边界: 仅 Llama 家族, 单请求 greedy, `max_cache_len` 与 `bucket_size` 显式, 首次捕获约 `13 ms/桶`, 不承担调度, 批处理或采样. 完整记录与未采纳方案 (含 INT8 LM head 因绑取主机标量不可图捕获的负结果) 见 R-052, 复跑入口 `examples/xqt_models/minicpm5_2b_graph_decode.py`, 产物 `artifacts/xqt/inference/minicpm5-2b/graph_decode_benchmark.json`.

2026-09-10 的 decode 运行时重写把同一 W4A16 路线从 `5.54` 压到 `3.49 ms/token`, 并把 QuaRot INT8 的可行性判定落到字节预算上. `CudaGraphDecodeSession` 现为单张 length-agnostic CUDA graph (`position` / `valid_len` 两个设备标量驱动 replay, 不再按 256 长度桶捕获, 不再需要零填充校正与 v_mask), 并新增两个 decode 专用 Triton 内核: 单遍 GQA decode attention (split-K 两段式, `valid_len` 在内核内由设备指针读取, K/V 每层只读一遍, 相对双 flash `48.2 -> 12.4 us/层` @L=3000) 与融合 RoPE + KV-scatter (HF split-half, cos/sin 预计算表按 position 索引). 同一 7976 字符文档: BF16 eager `25091 ms` (58.1 tok/s) -> BF16 graph `13123 ms` (steady 109.0); AWQ W4A16 native eager `28408 ms` (52.4) -> W4A16 graph `5273 ms` (steady `284.4 tok/s`), 相对本路线记录基线 (R-052 的 bf16 graph `16240 ms`) e2e `3.08x`, 相对 BF16 eager `4.8x`; 同运行时对照 (bf16 graph 换新运行时后 `13123 ms`) 为 `2.49x` (e2e) / `2.61x` (steady), 因为运行时重写同时加速了 bf16 路线. 新增 `int8_activations=True` 选项让线性层输入走 per-row INT8 量化/反量化 (QuaRot 式 INT8 激活 + 4-bit 权重, W4A8): w4a8_graph `5022 ms` (steady `288.1 tok/s`, 相对记录基线 `3.23x`), 质量 char BLEU-4 `0.607` (w4a16 为 `0.615`, eager 量化路线 `0.605`), 激活量化探针 logit RMSE `0.27`, 远小于 4-bit 权重自身的误差 `1.31`. 字节预算判定: decode 是 DRAM 带宽受限, 每 token 权重 bf16 `4.50 GB` / INT8 `2.25 GB` / W4 `1.13 GB`, 实测可达带宽 `590 GB/s` (AWQ GEMV 在 lm_head 形状 ncu 实测 `623 GB/s`, 95% SOL), 因此纯 W8A8 的现实上限约 `2.4x`, 3x 必须 4-bit 权重. 权重 layout 实验 (负结果): `kBlockSize 256->128` 使真实路线 `3.49 -> 3.75 ms/token`, 回退; `kOutputsPerBlock 2->1` 数值校验不通过, 回退; 分形状 cold 数据显示 o_proj (`302 GB/s`) 与 lm_head (`449 GB/s`) 是仅剩的空隙, 再挖需要 Marlin 式 permuted layout 或 split-K 重写内核. 完整记录见 R-053, 内核测试 `tests/xqt/kernels/test_decode_kernels.py`.

2026-09-10 的第二轮 decode 尾程优化消除了残差 add 与每 token 主机同步, 并给出带宽上界实测. 投影 epilogue 现在可直接吃 residual: AWQ decode kernel 的 `HasBias` 路径语义恰好是 "累加器 round 到输出 dtype 后在该 dtype 内加 bias", 与 `hidden = residual + projection(x)` 同构, 于是 `AWQW4A16Linear.bind_residual` 把 residual 同时作为 bias 与 output 传入, 一个 kernel 完成原地 residual 累加, 每层省掉 o_proj/down_proj 后各一次 elementwise add (共 84 个 kernel), 单测 `rtol=0/atol=0` 证明与未融合路径逐位一致, 任务质量 BLEU-4 `0.6153`/`0.6068` 与融合前完全相同. `CudaGraphDecodeSession.decode_batch` 把 greedy 回读改成分块 (默认 `readback_chunk=16`): 下一步输入只需写到设备 (图内 `self.token` 原地更新), 主机每 16 token 才同步一次, 省掉实测 `0.10 ms/token` (约 3%) 的 `token.item()` 同步代价; 代价是 EOS 回读超额最多 15 步, 由 `decode_steps` 如实计数. 顺带修掉一个真实缺陷: `_warm()` 的 eager 预热步会覆盖 `length-1` 槽位, 此前 capture 总在 prefill 之前所以被 prefill 覆盖掩盖, 一旦先 prefill 再 capture/decode_step 就会从第 1 个 token 起与 HF greedy 分叉; 现改为预热前后对该槽位 snapshot/restore, 并加回归测试. 最终五路线 (同一 7976 字符文档, 注意力与 GEMV 补测回退后的权威运行): BF16 eager `25701 ms` (56.7 tok/s), bf16 graph `13550 ms` (steady 106.0), w4a16 eager `29159 ms`, w4a16 graph `5081 ms` (steady 301.8)/w4a8 graph `5015 ms` (steady 300.3); e2e 相对同运行时 bf16 graph `2.67x`/`2.70x`, 相对记录基线 (R-052 旧运行时 `16240 ms`) `3.20x`/`3.24x`. 带宽上界实测把剩余空间量化清楚: 本机纯读上界 `697 GB/s`, 路线权重+aux `1.266 GB` 冷测 `2.34 ms` (540 GB/s, 77% 上界), 缺口集中在 CTA 单波小形状 (qkv `443`/o_proj `421` GB/s, 对比 lm_head `625`), 因为单波时全 CTA 同相位进 block 规约, 显存空转; 当前 `CuTile` 的 kernel catalog 已对齐上述 `TileLang` pattern, 即 `attention`, `conv`, `linear`, `norm`, `dense_linear_epilogue`, `dequant_gemm_epilogue` 及 packed FP4 / NVFP4 变体, 并保留原有 `bias_silu` pointwise scaffold. `CuTile` 仍是 metadata-first / reference-guarded engine: XQT 记录 artifact 和 capability, 并通过 `cuda.tile` 或兼容的 `cutile` 模块探测运行时; 内置 executor 可 materialize 线性 / dequant GEMM 的 reference-guarded 推理 wrapper, 但不把它当作完整通用执行器.

`PrecisionPolicy` 是 `xqt.convert(...)`, `xqt.nn` facade runtime intent 和 `gemm_with_precision(...)` 的统一静态精度 contract. GEMM 入口中的 `MatmulPrecisionSpec` 只保留为该类的 identity alias; role/mapping canonicalization 也由 `PrecisionPolicy` 提供. facade 的 `auto` 仍仅表示根据输入 dtype 延迟决策, 不构成第二套静态 schema.

新增的轻量算子转换入口使用 `xqt.convert(...)` 和当前真实的 `xqt.nn.*` facade. `Linear` / `Conv2d` / `LayerNorm` 是保留 PyTorch module/state_dict 语义并显式承载 engine 与 precision runtime intent 的 `torch.nn` 子类, 但不应写成已完成的完整 block-level lowering. `FeedForward` / `RMSNorm` / `Attention` / `TransformerBlock` 也是 semantic facade, 但 facade 不直接等于某个 kernel pattern. 这条入口面向单模块或小范围 operator conversion, 对外保持函数形态, 对内通过状态化 converter 完成 contract lowering 和 engine materialization. 其中 `xqt.nn.FeedForward` 采用固定 FFN 骨架 `norm? -> project-in -> activation/gate -> dropout? -> project-out`, 把 `norm`, `activation` 和 `fusion` 显式暴露为顶层配置, 并在模块内部优先复用现有 Triton GEMM epilogue 与 pointwise fastpath. 当前 `xqt.convert(feedforward, engine=..., policy=..., projection_policies=...)` 会把 `PrecisionPolicy` 注入 FFN runtime 配置: `policy` 作为整个 FFN 的默认精度意图, `projection_policies` 可进一步分别覆写 `proj_in` / `proj_gate` / `proj_out` 的 `activation/weight/bias/mma/accum/output` 字段. `engine="triton"` 会经由 shared `materialize_module(...)` 创建独立 FeedForward candidate 并保留 contract metadata; CPU 或 kernel 不可用时会显式记录 eager fallback. 同一套精度契约也接受 `A x B + C = O` 角色写法, 例如 `PrecisionPolicy.from_matmul(A="nvfp4", B="fp16", C="fp32", mma="fp16", accum="fp32", O="fp16")` 或 `policy={"A": "nvfp4", "B": "fp16", "C": "fp32", "MMA": "fp16", "ACCUM": "fp32", "O": "fp16"}`. 若希望避免长期直接传裸字典, 还可以使用结构化 `FeedForwardPrecisionPolicy(default=..., proj_in=..., proj_gate=..., proj_out=...)` 作为 `policy`. 对单次 GEMM / Linear 级别, `xqt.kernels.ops._impl.gemm_precision.gemm_with_precision(...)` 现在也支持 `engine=...`, 结构化 `MatmulPrecisionSpec(activation, weight, bias, mma, accum, output)` 及 `MatmulPrecisionSpec.from_roles(...)`, 作为更底层的统一 matmul 精度契约. `runtime_config()` 返回的是 engine, FFN 默认值, fusion report 和每个投影的最终生效配置. 当前 `activation/weight/bias/mma/output` 已进入模块内部 matmul 与输出路径; `accum` 已真实下推到 FFN 所复用的 Triton half/BF16 GEMM kernel, 并可通过统一 `MatmulPrecisionSpec` 进入相同的 GEMM 路径. 更低精度 GEMM 的真实执行仍依赖 packed contract 和 fused dequant GEMM path: `fp4` / `nvfp4` 可作为 Linear/FFN contract 的存储精度意图, dense eager fallback 不会伪装成真实低比特输出. FFN 的 Triton lowering 是复用已有 GEMM epilogue / gated pointwise kernels 的 candidate composition, 不是单个完整 FFN megakernel. `Attention` / `TransformerBlock` 也沿用语义块替换入口, 中间经 `materialize_module(...)` / wrapper 进入 engine, 再决定是一组 kernel 还是 megakernel. `optimize_hunyuan_ocr_svd_int4_blocks(...)` 是模型专用的 block composition: 它以 `w4a16_int4` 保存 SVD residual, 物化 INT8 MMA residual compute view, 对外层 `nn.ModuleList` 的每个逻辑 block 分别执行 `torch.compile`, 并用实际模型输入 warmup. 它不是 single fused block kernel; 若模型没有可识别的量化 block, helper 会报错而不是退化为 Linear 级优化. 它属于 `xqt` 子模块级 Provisional / Internal 能力, 不改变 `xqt.__all__` 顶层工作流入口集合.

operator stage 的运行时验收以 block 为准. `candidate_kind=single_kernel` 只表示替换一个子算子或小 wrapper, `candidate_kind=block_kernel` 表示替换完整 block. 当 `block_kernel` 目标使用 `engine=torch_compile` 并同时声明 `block_kernel` 与 `block_kernel_engine` 时, plan 会先尝试自动 block 图候选, 未应用时再运行手写 block kernel 后备; 两者仍共享同一个 `benchmark_target` block 边界.

配置单轨化已完成 Phase A/B/C: workflow 主链已通过 typed `StageSpec` / stage helper 消费 runtime config; workflow context 为 runtime-only, public `create_context()` 只接受 `OptimizationConfig` 或 workflow 输入; 旧 `load_xqt_config()` / `XQTConfig` / `XQTContext.config` 已删除. 最初诊断报告 1-8 的长期落地状态见 [architecture/xqt-realignment-guide.md](architecture/xqt-realignment-guide.md). 配置单轨化执行清单已完成并清理; 长期状态见 realignment-guide 与 FRAMEWORK.

`OptimizationConfig` 与纯 `StageSpec` schema 已下沉 `xqt.core.workflow_schema` / `xqt.core.stage_specs`;`pipeline`, `quant` 和 `readiness` 不再反向 import workflow 类型. `import xqt` 的公开入口全部按符号 lazy load,冷 import 只加载 `xqt` 自身且不拉起 XDL.

StageSpec 到 runtime Config 的转换统一使用 `xqt.core.stage_specs.stage_spec_to_config()`,不再由 workflow,pipeline 或 preflight 手工维护字段清单. 量化 strategy,`QuantScheme`,nature 与 canonical method/compute 的事实源统一为 `xqt.contracts.quant_strategy`;core schema,quant strategy resolver,capability 和三轴报告只从该契约派生. quantizer 公共 policy,模块替换,calibration 调用与 route adapter 工厂位于 `xqt.compression.quant.quantizers.base`.
